Nightly fbtriton — Design & Audit Report

Automated nightly .dev wheel selection for facebookexperimental/triton (main, base 3.8.0) · nightly series 3.8.0.dev<date> · generated 2026-07-17 · data via GitHub Actions check-runs / run-timing APIs

◆ Proposal

Version logic. A one-time repo commit bumps the base to 3.8.0 (setup.py + python/triton/__init__.py). Wheels keep a clean PEP 440 version — 3.8.0 (formal, → PyPI) or 3.8.0.dev<date> (nightly, → GitHub Release). The runtime triton.__version__ carries the fork/commit local segment: 3.8.0+fb (formal) or 3.8.0.dev<date>+fb.git<hash> (nightly). The nightly caller derives 3.8.0.dev<date> (base read from source) and wheels_fb applies it via setup.py's substitution hook to both TRITON_VERSION and __version__.

Selection logic. Fixed daily trigger (04:00 UTC) → read the last shipped commit from the nightly index (latest.json) → enumerate new commits since then → walk newest→oldest, pulling each commit's SHA-keyed check-runs (trigger-agnostic; a check is green if its latest run on that SHA passed — a rerun supersedes earlier runs; cancelled ignored) → first commit where all four required checks pass → build the shrunk matrix → upload to the rolling nightly Release, refresh the Pages index, prune > 30 nightlies. No new commits → exit silently. New commits but none green → file a tracking issue.

Storage & retention. Nightly wheels (cp312 + cp313 × x86_64 + aarch64) are uploaded as assets on a single rolling nightly GitHub Release (one tag, no per-day tags) behind a GitHub Pages PEP 503 index; a prune step keeps the last 30 nightlies. PyPI can't do this (~10 GB project cap, no delete API), so it's reserved for formal releases. Everything runs on GITHUB_TOKEN — no PAT or App token.

Install (nightly). pip install --pre fbtriton --index-url https://facebookexperimental.github.io/triton/nightly/simple/

1 · Context

Goal. Publish one fbtriton nightly .dev wheel per day to PyPI, built from a verified commit on main — not just whatever HEAD happens to be.

Why verification is required. On this fork, GitHub CI is not a merge gate. No ruleset defines required_status_checks. Commits are authored / reviewed inside Meta's monorepo and imported to public main via CodeSync/ShipIt — landing is allowed without CI signals. The GitHub Actions workflows run after a commit is already on main, so they are a post-merge monitoring signal. An arbitrary commit may therefore carry failing — or missing — CI, and the nightly must independently pick a green one.

Constraints that shaped the design:

  • Retention forces storage off PyPI. Full-matrix nightlies are ~2.4 GB/day, PyPI's project cap is ~10 GB, and PyPI has no delete API (manual, filenames burned) — so nightlies are hosted on a GitHub Release (binary asset storage) behind a GitHub Pages PEP 503 index, with a prune step keeping the last 30 nightlies. A shrunk ABI matrix (cp312 + cp313 × x86_64 + aarch64) further cuts volume. Formal releases still go to PyPI.
  • No exploded tags. Nightlies reuse a single rolling nightly Release (one tag) — assets are added and pruned, never a per-day tag.
  • Commit provenance. Baked into the runtime __version__ and a small latest.json manifest in the Release, which the next run reads back as the boundary marker (no state branch, can't drift).
  • Clean wheel versions. Wheels carry a plain PEP 440 version (3.8.0.dev<date>); the +fb.git<hash> local segment lives only in the runtime __version__ (PyPI would reject it, and it keeps the formal + nightly paths consistent).
  • H100 capacity. H100 runs frequently queue 20+h or never run, so selection is event-driven (walk back to the newest already-green commit) and never blocks on the queue.
  • No token. GITHUB_TOKEN manages Releases and deploys Pages, so no PAT or GitHub App is required.
